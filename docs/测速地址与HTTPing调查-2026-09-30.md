# 测速地址与 HTTPing 调查

日期：2026-09-30。性质：事实调查与建议，不代表已批准切换测速策略。未执行自动提交、推送的取数脚本，未修改业务代码或正式 IP CSV。

## 结论

存在实际命中 Cloudflare 缓存的大文件地址。本次候选为：

`https://cloudflare.cdn.openbsd.org/pub/OpenBSD/7.9/src.tar.gz`

本次 HEAD 返回 200、Content-Length 为 204451355 字节（约 204 MB / 195 MiB）；Range GET 返回 206，均观察到 CF-Cache-Status: HIT。该地址可作为 HTTPing 与下载共用 URL 的候选，但缓存命中和可用性只代表本次观测，不能保证所有边缘节点、时段都命中。

建议当前保留 TCPing 默认。先在实际使用网络、确认测试流量不经代理的条件下复验缓存候选，再决定是否切换 HTTPing。不要为了通过筛选直接把阈值从 200ms 放宽到 400ms。公共测速只能筛候选，最终质量仍需实际 VLESS 链路验证。

## 当前环境与验证边界

- 本地 cfst 为 v2.3.5，帮助输出与 VERSION.txt 一致。
- 本机 singbox_tun 处于 Up 状态；Find-NetRoute 对测试 IP 172.64.52.158 返回 singbox_tun。
- curl 使用 --noproxy '*' 和 --resolve 指定 IP；前者只能避开应用代理配置，不能绕过系统 TUN，后者也不能证明代理出口按指定 IP 连接。
- 本轮响应主要落到 LAX；TCP 建连约 2ms，而 TLS 完成常需约 0.7–0.9 秒。不能把这些数值解释为国内直连 Cloudflare 的质量。
- OpenBSD 候选在三个指定目标 IP（172.64.52.158、162.159.38.197、108.162.198.250）上分别执行 HEAD → Range GET → HEAD，九次均 HIT，Age 约 195608–195610 秒。由于 TUN 存在，不能声称验证了三个独立直连边缘。
- 仅发起 HEAD、小范围 GET 及小文件请求，没有执行全池测速或大文件吞吐测试；本轮未验证持续下载速度。

## HTTPing 实际测量什么

[v2.3.5 HTTPing 源码](https://github.com/XIU2/CloudflareSpeedTest/blob/v2.3.5/task/httping.go) 使用 HEAD：先进行一次未计时请求检查 HTTP 状态与地区码，再默认执行四次计时请求。HTTP 客户端允许复用连接，不能简单解释为每次都计入一次完整 TCP/TLS 握手。

TCPing 主要衡量 TCP 建连；HTTPing 衡量指定站点的 HTTP 响应过程，会受站点、缓存、连接复用和网络变化影响。二者不是同一指标，阈值不能直接照搬。HEAD 不下载整个大文件，文件大小主要关系到后续 GET 吞吐测量。

[Cloudflare 官方定义](https://developers.cloudflare.com/cache/concepts/cache-responses/) 中，DYNAMIC 表示请求未被判定为可缓存；HIT 表示命中缓存。交接文档把 HTTPing 慢 5–6 倍全部归因于 DYNAMIC，证据不足。未缓存是合理影响因素，尚缺相同出口、相同 IP、控制时间与请求方式的对照实验。

同一次 cfst 的 HTTPing 和下载共用 -url，没有原生独立的延迟 URL 参数。可以由脚本分两阶段编排，但需明确最后保存哪一阶段的延迟。使用本轮缓存大文件候选可先避免引入这项复杂度。

[下载源码](https://github.com/XIU2/CloudflareSpeedTest/blob/v2.3.5/task/download.go) 还指出未知 Content-Length 的响应提前结束可能导致测速值偏低；小文件测速低不能只归因于慢启动。交接中“约 95MB 封顶”仅为此前观测，本轮没有验证固定上限，也不把它视为官方永久限制。

## 代码与交接的差异

- tools/update-cf-ip.ps1 默认 TCPing，阈值 200ms、零失败、下载至少 5；默认保留最多 30 条。按延迟顺序尝试下载，找到足够合格者即停止，再按速度排序，不等于扫描全池后取得全局最快 30 条。
- 脚本只读取自身进程环境变量 BEST_IP_TEST_URL、BEST_IP_HTTPING。Docker 镜像运行 Node 服务，不运行该 PowerShell 脚本；Compose 的 .env 不会自动注入宿主 PowerShell。
- 下载阶段可以提取 colo，因此可以按本次地区码做后过滤。Anycast 不能保证固定地区，不等于不能过滤本次观测；过滤后数量不足则需要补测策略。本轮没有改变“不做区域过滤”的现有决定。
- 潜在可靠性问题：cfst 空结果不覆盖输出 CSV，而脚本没有在每轮前移除旧临时 CSV。上次异常遗留文件时，后续空结果可能读到旧数据；导入层也未独立复核延迟。此项仅记录，未修复。

## 黑框闪动调查

用户在本轮报告控制台黑框反复闪动。调查中确实启动了多次 console 子进程：Python 的两批并发 curl.exe 探测未设置 CREATE_NO_WINDOW，另有一次 cfst.exe -h。这是与本轮行为相符的高概率原因。

收到反馈后的后续 Python 子进程启动已显式指定 subprocess.CREATE_NO_WINDOW，协作调查也停止启动额外测速进程。进程快照存在 Codex、PowerShell 及其他长期运行程序的 conhost；conhost 存在不代表窗口可见。未捕获闪动窗口的句柄和瞬时 PID，不能断言全部黑框都来自某一进程，也不能据此认定 Codex 更新引入回归。

后续外部程序应使用无窗口启动；若仍发生闪动，应在发生时关联窗口 PID 与父进程，避免凭窗口颜色判断来源。本轮未更改系统代理、后台服务或应用设置。
